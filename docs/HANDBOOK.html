AGENTPROOF / 01

AgentProof

Four agent applications. One durable execution platform. Evidence you can inspect.

A Python monorepo implementing the five portfolio requirements in the supplied reference: grounded ReAct research, bounded code repair, specialist support routing with human approval, parallel report generation, and an operations layer for deployment. A responsive operations dashboard ships with the API.

Release status: production-oriented implementation, locally validated; not deployed or certified production-ready. Live model/search credentials, a real Docker runner, PostgreSQL integration, identity-provider integration and cloud acceptance remain release gates. See validation evidence and release gates. No live accuracy, repair success rate, cost saving or cloud uptime is invented.

Start locally

Python 3.12+ is required. Run commands from the repository root.

python -m venv .venv
source .venv/bin/activate
pip install -r requirements.lock
pip install --no-deps -e .
export DEV_API_TOKEN="$(python -c 'import secrets; print(secrets.token_urlsafe(32))')"
export DATABASE_URL=sqlite:///agentproof.db
agentproof migrate
agentproof api

Open http://localhost:8000, paste the development token, and connect. The UI and API work without provider credentials; agent execution requires the live provider settings below. The development identity cannot approve its own refund requests.

In a second terminal, activate the same virtual environment and export the same database/auth/provider variables:

export LLM_BASE_URL=https://api.openai.com/v1
export LLM_API_KEY=your-provider-key
export LLM_MODEL=your-json-capable-model
export TAVILY_API_KEY=your-search-key
agentproof worker --kinds research support reports

The model must support OpenAI-compatible Chat Completions, response_format=json_object, and max_tokens. This is a specific adapter contract, not a claim that every model/provider is compatible. Keys are read from the process environment; no .env auto-loader is used for native commands. Docker Compose does load .env.

Code repair uses a separate runner with Docker. It is intentionally excluded from the general worker command. Follow the runner setup.

pytest -q
python scripts/evaluate.py --suite support --mode baseline --output evals/results/support-baseline.json
python scripts/incident_drill.py

AGENTPROOF / 02

Architecture and design

Objective and boundaries

AgentProof is an inspectable engineering portfolio with a shared runtime that makes four agent patterns executable. Each pattern has a distinct risk: unsupported claims, unsafe code execution, unauthorized financial actions, or unsubstantiated parallelism benefits. The fifth project is the infrastructure needed to run those patterns reliably.

The implementation supports bounded asynchronous jobs, persistent progress and human intervention. It does not include autonomous repository merging, payment execution, arbitrary browsing, vector retrieval, Kubernetes provisioning, or a hosted identity provider. Those are separate integrations, not hidden stubs. The application never substitutes scripted responses when credentials are missing.

Components and ownership

Component Responsibility Important boundary
FastAPI service Authenticate, validate, enforce tenant scope, enqueue, stream, approve, cancel Does not execute user code or LLM work in HTTP handlers
Store Transactions, admission limits, leases, events, checkpoints, decisions and refund ledger Sole writer of durable application state
Worker process Claim one job, heartbeat, run bounded workflow, commit or retry One active job per process; scale processes for concurrency
Workflow context Memoized stages, persistent model-call budget, traces Cached stages prevent many repeated calls after restart
Model adapter JSON responses, schema validation, timeout, token usage, cost estimation Server-owned endpoint; not request-configurable
Search adapter Tavily snippets and source metadata No arbitrary URL fetcher, filesystem connector or browser
Docker sandbox Execute submitted Python source/tests with hard resource limits Dedicated host and restricted container; no fallback to host execution
Dashboard Submit jobs, inspect results, replay events, export trace, approve as authorized user Token held in page memory, no localStorage or query-string token

Submission path

The authenticated principal supplies tenant and subject; request payloads cannot override either. Input schemas reject unknown fields and bound text sizes. A request must provide an idempotency key. The store hashes the workflow kind plus normalized payload. Reusing a key with the same content returns the original job; changing content returns HTTP 409. The uniqueness boundary is (tenant, idem_key).

A per-tenant sentinel row serializes admission checks so concurrent submissions cannot bypass the active-run limit. Queued, running and approval-waiting jobs all consume capacity. The default limit is 20 active jobs per tenant. This is an admission limit, not a complete HTTP rate limiter or financial budget.

Claiming and recovery

PostgreSQL claim transactions select eligible rows with FOR UPDATE SKIP LOCKED, ordered by creation time. SQLite development transactions use BEGIN IMMEDIATE and WAL. These are different concurrency mechanisms; SQLite tests do not validate PostgreSQL behavior.

A successful claim increments an attempt counter and creates a random lease token. Every checkpoint, result, event, heartbeat and refund-ledger write verifies both the token and the unexpired running state under a row lock. An expired or replaced owner cannot commit. A worker crash leaves the job recoverable after its lease expires. The default lease is 120 seconds with a heartbeat approximately every 40 seconds.

Delivery is at least once. Completed steps are durable, but a crash after a provider accepted a request and before the checkpoint commits can repeat that external request. Fencing prevents stale database writes; it does not undo an already-started provider call. Provider billing may therefore exceed the successful-response usage recorded locally. The repo deliberately does not promise exactly-once LLM execution.

Checkpoints and retry semantics

Each named step saves a JSON result inside the run checkpoint. A resumed workflow reconstructs the same control flow and returns stored values for completed steps. The names are stable workflow identifiers; renaming them without a migration changes replay semantics. Model call reservations persist before the provider call, providing a conservative cap of 24 calls per run.

Transient network errors, HTTP 429 and provider 5xx responses cause bounded whole-job retries with delays of 2 ** attempt seconds. Permanent authentication/schema errors fail the job. Maximum worker claims before exhaustion: three, excluding the intentionally reset claim count after a human decision. Code repair has a separate maximum of three patch attempts inside a workflow. These two limits must not be confused.

The worker's run deadline is 600 seconds. Cancellation changes state and invalidates the lease. It prevents later commits; in-flight provider calls or sandbox work may continue briefly until the worker sees fencing or heartbeat failure. Containers have their own timeout and cleanup.

Human decisions

A support request may propose a refund using an order ID and amount in integer cents. Both values are frozen in the original payload. A model can request review but cannot approve. The API requires a refund_approver role and a subject distinct from the original requester. Decision insertion and requeue happen in one transaction. The worker resumes from its route/reply checkpoints, reads the decision and inserts at most one ledger record per run.

The ledger status is approved_pending_payment_integration. No money is moved. Order ownership, previous refunds, payment capture validation, currencies, accounting reconciliation and an idempotent payment-provider outbox are release work before enabling real refunds.

Streaming and observability

Events are stored in the database with increasing IDs and timestamps. The SSE endpoint replays events after a cursor, including across API replicas. Each connection lasts up to 60 seconds and can reconnect with Last-Event-ID or after. The browser uses authenticated fetch, not query-string tokens. Streaming means execution events; model token streaming is not implemented.

OpenTelemetry spans record run and step boundaries. Workflow spans are connected within one process execution. A resumed claim creates a new trace, correlated by run.id; distributed W3C trace propagation across retries is not implemented. Prometheus exposes HTTP counts and latency. Queue-age and workflow metrics are currently operational SQL queries, not exported gauges.

Event summaries omit prompts, but checkpoints, original payloads and final results contain user content and retrieved snippets. Encryption at rest, backup controls and retention must be configured at the database/platform boundary. User-facing traces must be treated as sensitive artifacts.

Capacity model

Each worker handles one run at a time. A report run fans out three model calls concurrently, then synthesizes. The model adapter allows four concurrent calls per worker process. Aggregate concurrency is therefore bounded by replica count times four, not a global distributed limit. Size replicas against provider quotas and PostgreSQL connections. Large evidence corpora and long reports exceed this release's deliberately bounded payload and token limits.

Data integrity

The ER diagram shows logical relationships. Run IDs in events/approvals/refunds are indexed or unique as needed but are not all SQL foreign keys. The application currently has no deletion API, avoiding partially deleted runs. A future retention process must delete dependent rows transactionally. The schema has an initial version record and a readiness check; follow-on schema upgrades need explicit versioned migration scripts.

Technology choice

Python, FastAPI, SQLAlchemy and PostgreSQL provide an accessible service boundary and transaction model. The workflows use explicit async functions and durable steps instead of depending on an agent framework's opaque replay semantics. This is intentional: the four patterns do not require LangGraph to be valid. A framework adapter can be added later without weakening store ownership and approval rules.

API contract and examples

Interactive OpenAPI: /docs. Machine-readable specification: /openapi.json. All business endpoints require Authorization: Bearer TOKEN. Tenant identity comes from the verified token. Health endpoints and static UI assets are public; metrics require operator.

Method and path Behavior
POST /v1/runs Validate and enqueue; returns 202 with {run, created}
GET /v1/runs Latest 100 jobs belonging to the caller's tenant
GET /v1/runs/{id} Result, input, status and timestamps; private lease/checkpoint fields excluded
GET /v1/runs/{id}/events SSE replay after an event cursor, up to 60 seconds per connection
GET /v1/runs/{id}/traces?after=ID Up to 500 event records; continue with the last ID
POST /v1/runs/{id}/approval Role-protected, distinct-human decision on a waiting support run
POST /v1/runs/{id}/cancel Invalidate a queued/running/waiting job's ownership
GET /health/live API process liveness
GET /health/ready Database reachable and schema version 1 present
GET /metrics Prometheus HTTP metrics, operator role required

Research example

curl http://localhost:8000/v1/runs \
  -H "Authorization: Bearer $DEV_API_TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: research-demo-001' \
  -d '{"kind":"research","payload":{"question":"What does SKIP LOCKED mean for a PostgreSQL queue?"}}'

Save the returned run ID. Poll the run or stream events:

curl -N "http://localhost:8000/v1/runs/$RUN_ID/events" \
  -H "Authorization: Bearer $DEV_API_TOKEN" \
  -H 'Last-Event-ID: 0'

A successful research result contains accepted claims, rejected claims with reasons, source metadata, limitations and an abstention flag. Absence of evidence can produce a successful execution with abstained=true; success of the workflow does not imply a factual answer exists.

Inputs

Research: question, 5–2,000 characters.

Code repair: issue, 5–4,000 characters; source, at most 30,000 characters; tests, 10–30,000 characters. The harness expects solution.py and Python unittest tests importing from solution.

Support: message, 3–4,000 characters; optional order_id, a bounded alphanumeric/underscore/hyphen identifier; optional refund_cents, positive integer up to 100,000. This maximum is a proposal limit, not refund eligibility. A refund with missing order/amount completes with escalation and needs_order_and_amount.

Reports: topic, 5–2,000 characters; evidence, 50–20,000 characters; optional benchmark, default true. Disabling the benchmark omits the single-agent baseline and saves that model call.

All input objects reject additional fields. The HTTP body cap is 100,000 bytes, independent of the declared Content-Length. Upstream proxies should also impose body and read-time limits.

Approval example

curl -X POST "http://localhost:8000/v1/runs/$RUN_ID/approval" \
  -H "Authorization: Bearer $APPROVER_OIDC_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"decision":"approved","reason":"Duplicate charge reviewed against the order record"}'

The approver must be in the same tenant, have refund_approver, and have a different subject from the requester. The same run cannot receive a second decision. A rejection resumes the run and records rejection without a refund ledger entry.

Status and errors

Status values: queued, running, waiting, succeeded, failed, cancelled. API errors: 401 missing/invalid identity; 403 insufficient role; 404 absent or another tenant's run; 409 idempotency/state/self-approval conflict; 413 body too large; 422 schema error; 429 tenant active-job capacity reached.

Worker failures store an error class, not raw provider bodies, keys or stack traces. Inspect trace events and sanitized worker logs for diagnosis. A missing provider key causes an explicit failure, never a synthetic answer. The export CLI is an administrative database operation and is not tenant-filtered; restrict shell/database access accordingly.

AGENTPROOF / 05

Evaluation design and evidence

Evidence levels

  1. Deterministic tests: Verify application behavior using synthetic inputs, scripted model doubles and real local database transactions.
  2. Rules baseline: Measures a simple classifier on the 50-case support dataset. It is independent of the live support model.
  3. Live integrations: Exercise actual model/search responses and Docker. Require credentials and an isolated runner.
  4. Deployment acceptance: Verify PostgreSQL under concurrency, real OIDC, ingress, restarts, backup/restore and load in the target environment.

A result at one level does not imply success at another. Stored reports include dataset SHA-256, mode, timestamp, per-case outcomes and model identity where applicable. Do not copy rules-baseline results into a model accuracy slide.

Support: 50 cases

The authored dataset has 18 billing, 16 account and 16 technical cases. Categories include routine requests, paraphrases, ambiguity and prompt injection. Expected routing labels are authored judgments, not independently adjudicated production ground truth. Classifier accuracy does not establish refund safety; separate tests enforce the authorization boundary.

Measured local rules baseline: 43 correct of 50 (86%), macro-F1 0.8619. Approximate 95% Wilson interval: 73.81%–93.05%. This interval assumes independent cases; because these are curated synthetic examples, it is descriptive rather than evidence of real-world generalization.

Expected / predicted Billing Technical Account
Billing 15 3 0
Technical 1 14 1
Account 0 2 14

Errors include indirect billing/access requests and mixed-topic messages. Keep the initial result unchanged as a baseline; improving heuristics on these same cases would overfit the evaluation set.

python scripts/evaluate.py --suite support --mode baseline --output evals/results/support-baseline.json
python scripts/evaluate.py --suite support --mode live --output evals/results/live-support.json

The live runner includes failed jobs in the denominator. Add a separately authored, frozen holdout before making production accuracy claims. Measure per-class recall, escalation recall, injection resistance and confidence calibration. The current model's numeric confidence is not calibrated by this release.

Code repair: 20 issues

Each issue has broken Python source, a natural-language requirement, public regression tests and hidden input cases. Hidden tests are never supplied to the model. Tasks span arithmetic, sequences, strings, sorting, parsing and interval merging. They are small synthetic tasks, not a substitute for SWE-bench or a real repository issue distribution.

A live workflow first confirms a failing baseline, then runs at most three repair attempts. Success on public tests is followed by a separate held-out sandbox execution. The evaluation reports public and hidden outcomes, attempt count, latency and failures for every issue. The denominator is all selected issues, including infrastructure failures.

export SANDBOX_ENABLED=true
python scripts/evaluate.py --suite codefix --mode live --output evals/results/live-codefix.json

Report hidden_pass_count / 20, public-vs-hidden gap, pass by attempt, infrastructure errors and token cost. The script permits --limit for smoke checks and records the actual smaller denominator. No repair pass rate has been measured in this environment because Docker and live model credentials are unavailable.

Research grounding

The workflow validates citation identity and verbatim quote containment before asking an entailment judge. This blocks invented source IDs and invented quotations but does not prove the source is correct. A judge can share the answer model's biases. Search snippets can omit context, change over time or contain injection.

python scripts/evaluate.py --suite research --mode live --output evals/results/live-research.json

The included live research case is a smoke case, not a statistically meaningful benchmark. Expand to a frozen question set with independent assessors, known unanswerable questions and malicious source snippets. Score citation precision, supported-claim precision, answer completeness, abstention correctness, source quality and search cost. Tests already cover exact-match rejection and unsupported-claim abstention.

Reports: honest parallel comparison

The live report suite repeats the same fixed task five times. Each run has three specialist calls plus supervisor synthesis, then a single-agent call on the same topic/evidence. The same model and per-call output cap apply. Multi-agent therefore has a larger total call/token budget, and the default order is fixed. These are explicit confounders.

python scripts/evaluate.py --suite reports --mode live --output evals/results/live-reports.json

Compare successful runs' latency, token use and estimated model cost, while reporting failures separately. Before claiming an advantage, randomize execution order, use multiple topics, repeat enough trials, and have blinded reviewers score correctness, coverage and usefulness. Exact evidence quotes are only a lexical check; the release does not provide a comprehensive quality judge or demonstrate that multi-agent is better.

Cost accounting

For each completed model response:

estimated USD = (input tokens × input rate + output tokens × output rate) / 1,000,000.

Set LLM_INPUT_USD_PER_MILLION and LLM_OUTPUT_USD_PER_MILLION to verified prices for the chosen model. If prices or provider token counts are absent, cost is null, not zero. The estimate excludes search charges, compute, database, storage, network, cached-token discounts, reasoning-token nuances and any provider request whose usage was lost before a durable event. These are model response estimates, not a billing reconciliation.

Reproducibility

Commit the dataset and prompt changes together with raw results and environment metadata. Keep live traces private until reviewed for sensitive content. CI publishes validation artifacts but does not call paid providers. Lock dependencies for repeatability, record the model revision if supported, and retain date/source snapshots for search evaluations. The source archive includes the local test and drill evidence actually generated during creation.

Threat model and security boundaries

Trust zones

The browser, customer messages, retrieved snippets, proposed source code and submitted tests are untrusted inputs. The API, queue worker and database are trusted application components. The model/search services are external processors. The Docker runner is privileged infrastructure and must live on a dedicated host; test containers are the untrusted execution boundary.

Controls and residual risks

Threat Implemented control Remaining requirement
Cross-tenant access Tenant derived from verified JWT; tenant-filtered reads/mutations; isolation tests Database row-level security and tenant-specific encryption are not implemented
JWT forgery RS256 allowlist, signature, issuer, audience, expiry, required tenant/subject, bounded claims Validate real issuer configuration, key rotation, revocation and outage behavior
Duplicate jobs Tenant/idempotency-key uniqueness and request-content hash Browser submit creates a fresh key per click; use a stable key for network retries
Stale worker writes Lease token, running-state and expiry checked under lock External requests may still complete after lease loss
Unauthorized refund Distinct role-bearing approver, frozen proposal, unique ledger No payment integration or order ownership checks; keep ledger nonfinancial
Prompt injection Strict schemas, untrusted-data prompts, small tool surface, no arbitrary actions Prompt instructions alone are not a security boundary; models can misclassify or hallucinate
Sandbox abuse No network, read-only root, non-root UID, no capabilities, no privilege escalation, CPU/memory/PID/time/output limits Shared-kernel container risk remains; use microVM/gVisor isolation for hostile public workloads
Credential theft Keys from environment; no key in browser, checkpoint, model prompt or query string Secret manager, process isolation, credential rotation and provider-scoped keys
Resource exhaustion Body and field limits, bounded loops, run deadline, admission cap, call cap, worker semaphore Gateway rate limits, global provider quotas, spend budgets, connection/read timeouts
XSS UI renders results with textContent, restrictive CSP, no third-party scripts Full penetration test and accessibility/browser matrix
Sensitive traces Tenant-scoped trace endpoints, payload-free event summaries Checkpoints/results still contain data; retention, backups, DLP and encryption at rest

Identity contract

Production mode rejects SQLite and development-token authentication. Configure an HTTPS JWKS endpoint, issuer and audience; JWTs must contain sub, tenant_id, iat, exp, and optionally a list of roles. The trusted issuer owns tenant and role assignment. Tokens cannot self-select a tenant from request JSON.

refund_approver authorizes human decisions; operator authorizes metrics. Other authenticated users can operate jobs within their tenant. Per-user ownership ACLs inside a tenant are not implemented. A development token authenticates one fixed local identity with operator privileges, not refund approval privileges.

The dashboard accepts a bearer token for a technical demo. It does not implement browser OAuth authorization-code/PKCE login, refresh tokens or a session BFF. Add your organization's login flow before exposing it to end users.

Code runner specifics

The sandbox starts a new container for every baseline, candidate and hidden test run. Source/tests arrive over stdin, not host-mounted directories. It receives no application secrets or Docker socket. Its Python harness writes only to a bounded tmpfs, captures limited output and runs unittest with a 15-second subprocess limit. The host bounds the container operation to 25 seconds and explicitly removes the container even if the client times out.

This release is for trusted internal engineering users working on reviewed Python tasks. Submitted tests and source share an interpreter during unittest discovery, so malicious code could tamper with test machinery or fake success. A green sandbox result is not a trust proof. Before accepting public arbitrary code, replace the execution boundary with independently managed microVM jobs, trusted evaluation harnesses, syscall policy, artifact verification and a separate hidden evaluator. Never mount the host Docker socket into the API or general worker containers.

Data handling

No retention sweep runs automatically. Operators must define retention, legal deletion, archival and backup policies before real customer data is ingested. Do not place payment card data, secrets, private keys or regulated records in sample jobs. Exported traces can include original inputs and final outputs. The administrative CLI can access every tenant because it runs with direct DB credentials; restrict this path to authorized operators.

Secure release checks

Run dependency and container vulnerability scanning, pin deployed images by digest, configure TLS and egress allowlists, test authentication against the actual identity provider, set provider spend ceilings, review role assignment and perform an isolated sandbox breakout assessment. These are target-environment gates, not completed checks in this artifact.

Deployment guide

Modes

Mode Persistence Authentication Purpose
Native local SQLite WAL Random development bearer token Development and deterministic tests
Docker Compose PostgreSQL 16 volume Development or configured OIDC Integrated staging-style local environment
Kubernetes target External managed PostgreSQL OIDC/JWKS, no development token Target deployment after release gates

No cloud environment is created or deployed by this archive. The Kubernetes YAML is a starting manifest that must be configured for your environment. The repair worker is deployed separately on an isolated runner host.

Native local process setup

Install from requirements.lock and install the package with --no-deps -e .. Set DATABASE_URL and a random DEV_API_TOKEN, then run agentproof migrate once. Start agentproof api and agentproof worker in separate terminals sharing the same variables. The app does not source .env automatically outside Compose.

Docker Compose

Copy .env.example to .env. Replace the PostgreSQL password in both POSTGRES_PASSWORD and DATABASE_URL. Set the API token, provider URL/key/model and Tavily key. Leave unknown token prices unset. Then run:

docker compose config --quiet
docker compose up --build -d
docker compose ps
curl --fail http://localhost:8000/health/ready
docker compose logs --tail=100 worker

The migration service completes before API and worker start. The default worker handles research/support/reports. The collector writes basic trace summaries to logs; configure an authenticated OTLP backend for retained traces. Database data survives container replacement in postgres-data. docker compose down -v deletes that volume and is destructive.

Dedicated code repair runner

Use a dedicated Linux VM or isolated runner host with a rootless Docker daemon where possible. Install Python 3.12 and this package. Pre-pull the sandbox image, preferably pinning a reviewed digest. Set the same reachable database URL and model settings, then:

docker pull python:3.12-slim
export SANDBOX_ENABLED=true
export SANDBOX_IMAGE=python:3.12-slim
agentproof worker --kinds codefix

A native worker requires an accessible Docker CLI and daemon. If the database is in Compose, db resolves only inside its network: use a deliberately exposed private database address or a shared managed database with TLS. Do not expose PostgreSQL publicly to make the runner connect. The general Compose deployment intentionally does not mount a Docker socket or start privileged nested Docker.

Enable the integration check only on the isolated runner:

RUN_DOCKER_TESTS=1 pytest -q -m docker

The default mutable image tag is suitable for development only. Production must use a reviewed digest and a sandbox infrastructure threat review.

Kubernetes target

  1. Build and scan the image; push to your registry and substitute its digest in infra/k8s/base.yaml.
  2. Provision managed PostgreSQL with TLS, backups and a tested restore path. Supply sslmode=verify-full and trusted CA configuration as appropriate for the provider.
  3. Create the agentproof namespace and a Secret named agentproof-runtime using your secret manager. Set ENVIRONMENT=production, DATABASE_URL, JWT_ISSUER, JWT_AUDIENCE, JWKS_URL, LLM_API_KEY, LLM_MODEL, LLM_BASE_URL, TAVILY_API_KEY, optional prices and OTLP settings. Do not set DEV_API_TOKEN in production.
  4. Apply the migration Job first and wait for completion. Then apply API/worker deployments and Service. The combined YAML lists the Job first, but Kubernetes application order does not itself wait for migration completion; use your deployment pipeline to enforce this gate.
  5. Add your TLS ingress with request size, rate, read timeout and SSE buffering settings. The sample ingress policy assumes an ingress-nginx namespace; change selectors for your controller. No public ingress hostname or certificate is supplied.
  6. Add environment-specific egress restrictions to the database, identity provider, model gateway, search provider and telemetry backend. The provided NetworkPolicies restrict ingress only.
  7. Deploy the separate code worker and verify its private database connectivity and isolation.
  8. Run the acceptance checklist. Roll out gradually and retain the previous image digest.

Acceptance checks

  • Health probes pass and migration version matches.
  • Real signed JWTs work; wrong issuer/audience, expired tokens and cross-tenant access fail.
  • A live research answer contains actual sources and a replayable trace.
  • A repair runs real public and hidden tests in Docker; generated code never executes on the host.
  • Refund requester cannot self-approve; a second identity can approve; repeated decisions cannot create duplicate ledger entries.
  • Worker termination mid-run causes lease recovery with checkpoint reuse; stale commits are rejected.
  • SSE reconnect preserves cursor order and leaks no other tenant's events.
  • Backup restores a known run, its checkpoints, approval and events in an isolated environment.
  • Load and provider quotas are tested before setting replica counts.

Rollback

Stop admission at the ingress, allow active jobs to finish where practical, then roll back API and workers to the previous image. Keep database contents. This initial release has only schema v1; future incompatible migrations require a forward/rollback data plan. Do not run older workflows over newly shaped checkpoints unless compatibility was tested. Prefer additive fields and stable checkpoint names.

AGENTPROOF / 08

Operations and reliability runbook

Proposed service objectives

These are targets to validate, not measured SLO attainment: 99.9% API availability, admission p95 below 300 ms, queue wait p95 below 10 seconds at planned capacity, zero unauthorized refund ledger writes, and recovery after worker loss within lease duration plus queue delay. Provider latency, search quality and human approval time have separate budgets.

Monitoring

HTTP counts and latency are available at authenticated /metrics. OpenTelemetry traces record run and step boundaries. Use structured event JSON for workflow progress, model usage and state changes. Do not log provider keys or raw exception responses. Correlate by run ID across worker retries.

Operational PostgreSQL queries:

SELECT status, count(*) FROM runs GROUP BY status;
SELECT kind, min(created) AS oldest_created, count(*)
FROM runs WHERE status = 'queued' GROUP BY kind;
SELECT id, tenant, kind, attempt, lease_until
FROM runs
WHERE status = 'running' AND lease_until < extract(epoch FROM now());
SELECT id, kind, error, updated FROM runs
WHERE status = 'failed' ORDER BY updated DESC LIMIT 50;
SELECT id, tenant, updated FROM runs
WHERE status = 'waiting' ORDER BY updated ASC;

Treat direct SQL access as administrative. Tenant isolation is enforced by the application, not automatically for arbitrary database queries. Alert on old queued jobs, expired leases, error spikes, waiting approvals exceeding the support SLA and repeated provider 429s.

Queue backlog

Check whether workers are running with the correct --kinds. Code jobs will remain queued until a dedicated code worker exists. Check provider authentication, network access and database connections. Increase replicas only after checking provider quotas. All active runs, including waiting approvals, count against the tenant cap. Resolve aged approvals rather than raising the limit indefinitely.

Provider failures

401/403 or invalid structured response: fix the key/model/adapter contract and submit a new run with a new idempotency key. The application does not endlessly retry permanent errors. 429/5xx and network errors retry up to the claim limit with bounded backoff. No circuit breaker or cross-replica rate limiter is shipped; a provider outage can affect all workers. Use a gateway with shared quotas/circuit policy for a scaled deployment.

Lost worker

Inspect the run lease and event history. A crashed worker's lease will expire, allowing another worker to claim and reuse checkpoints. Do not manually set status=succeeded to unblock a queue. If a worker repeatedly crashes on the same job, the attempt cap eventually marks it failed. Investigate payload size, adapter failures and sandbox errors before resubmission.

Cancellation

The cancel endpoint fences database mutations immediately. It is not a guarantee that an already-started external provider call is cancelled or free. The worker observes ownership loss at its next checkpoint or heartbeat, then cancels local tasks. The sandbox cleanup explicitly removes its container. Run-level deadlines and per-container limits provide independent bounds.

Refund approval

Inspect the original proposal and verify the order in your actual business system. Use a separate authorized identity. Approving writes only the local pending-integration ledger. Do not tell the customer money was returned based on that status. Rejected proposals complete without a ledger entry. If a payment integration is added, require a transactional outbox, provider idempotency key, webhook verification and reconciliation before any funds-moved status.

Backups and retention

Use managed database snapshots plus point-in-time recovery. Perform a restore drill into an isolated database and compare run/event/approval relationships. Define RPO and RTO with the deployment owner. No backup schedule, retention job or deletion API is automatically configured by this repo. Payloads, evidence and checkpoints may contain sensitive data. Archive/redact deliberately and delete dependent rows transactionally when adding retention.

Run python scripts/incident_drill.py in a development checkout. It creates an isolated temporary database, checkpoints a job, expires its lease, reclaims it and attempts a stale completion. The stale completion must be rejected and the recovered owner must succeed. The script writes real local evidence to evals/results/incident-drill.json. See the one-page incident write-up.

Incident exercise: stale worker after lease expiry

Classification: deliberate local fault-injection exercise, not a customer outage or claimed production incident. Scope: one synthetic research job in a temporary SQLite database. Evidence: evals/results/incident-drill.json; reproduction: python scripts/incident_drill.py.

What was caused

An active worker checkpointed a successful retrieval stage. The drill then forced its lease timestamp into the past while preserving the original worker's token. This models a worker that misses heartbeats because of process suspension, a long runtime pause or network partition, but later resumes and tries to commit.

Observed sequence

  1. Worker A claimed a job and persisted retrieved evidence.
  2. The operator injected lease expiry directly in the drill database.
  3. Worker B reclaimed the job with a new token and attempt number.
  4. Worker A attempted to commit a stale result and received LostLease.
  5. Worker B committed the recovered result, with the earlier checkpoint intact.

The timestamped JSON artifact records these events from the actual run. No synthetic latency or customer-impact estimate is attached.

Root failure mode

A lease is not enough on its own. An old worker may continue executing after the lease has expired and another worker has taken ownership. Without a fencing check on every mutation, it can overwrite the new owner's state, duplicate decisions or append misleading completion events.

Containment and fix demonstrated

The Store checks current status, unexpired lease and random ownership token under a row lock before every mutable worker operation. Reclamation changes the token. Cancellation clears ownership. Checkpoints are reused by the recovered owner. The old worker's completion is therefore rejected, and only the new owner publishes the final result.

What this exercise proves

The local SQL implementation preserves the checkpoint and rejects a stale database commit during the injected sequence. It does not prove PostgreSQL behavior under distributed load, network partition safety for provider calls, exact recovery-time objectives or exactly-once external execution. PostgreSQL concurrency and real worker-kill drills remain deployment gates.

Follow-up

Run the same scenario against staging PostgreSQL with two real worker processes; kill one during a provider call; measure recovery and duplicate provider billing. Add queue-age alerts and stalled-job dashboards. Preserve idempotency at each future side-effect boundary. A payment system would require a transactional outbox and provider reconciliation in addition to the current local ledger uniqueness constraint.

Architecture decision records

ADR 001 — Transactional database queue

Accepted. Use PostgreSQL for queue state, checkpoints, events and approval transactions. This keeps approval/requeue and result/event writes atomic and avoids dual-write problems in this bounded portfolio. SKIP LOCKED supports multiple consumers. Trade-offs: database polling, operational connection load, no broker-level fanout, and contention at larger scale. Revisit a broker/outbox design when workload volume warrants it. SQLite is development-only.

ADR 002 — Explicit workflow code

Accepted. Express the four patterns as async Python functions using named durable steps. This keeps replay behavior visible and limits framework coupling. Trade-offs: no visual graph editor, framework-managed checkpoint migrations or built-in graph inspection. A future LangGraph adapter must preserve tenant ownership, approval separation and store fencing rather than duplicating state authority.

ADR 003 — Event streaming instead of token streaming

Accepted. SSE exposes durable workflow events, giving replay across replicas and resumable UI inspection. Model outputs use structured JSON and are committed as whole steps. Trade-offs: users do not see incremental model tokens; long model calls may have only heartbeat events until completion. Token streaming would need partial-output semantics that do not bypass final validation.

ADR 004 — Refund ledger without payment execution

Accepted. Demonstrate the human approval pattern using an immutable local ledger with an explicit pending-integration status. No payment API is called. Trade-off: not a real refund product. Actual payment integration requires eligibility checks, idempotent outbox dispatch, verified callbacks and reconciliation.

ADR 005 — Restricted Docker execution

Accepted for trusted internal tasks only. No network, capabilities, host mounts or credentials inside test containers; non-root execution, bounded resource/time/output limits. The runner itself lives separately. Trade-off: Docker shares a kernel and submitted source can tamper with Python tests. Public hostile workloads require stronger isolation and a trusted independent judge.

ADR 006 — Evidence before performance claims

Accepted. Baseline, scripted-test and live results remain separate. Unknown costs are null, not zero. Multi-agent reports are compared against a single-agent path without assuming an improvement. Trade-off: the initial artifact does not contain fabricated impressive live benchmark numbers. This strengthens the portfolio's credibility.
